 [측정 지표 파싱 방법]

  지표              파싱 위치                                  단위
  ─────────────────────────────────────────────────────────────────────────────
  OPS 시계열        "thread X: (...) ops/second in (...) s"   ops/sec (초별)
  Read OPS          "readrandom : X micros/op Y ops/sec"      ops/sec (요약)
  Write Stall 시간  "rocksdb.db.write.stall ... SUM : X"       마이크로초 합산
  WAF (쓰기증폭)    compact.write.bytes / bytes.written        배율 (1.0 = 증폭 없음)
  WAF 계산식        WAF = (bytes_written + compact_write_bytes) / bytes_written

  ※ rocksdb.db.write.stall SUM은 4스레드 합산값. 상대 비교용으로 활용.

 [Part 1: MemTable 크기 스윕 실험]  —  run_memtable_exp.sh
================================================================================

  연구 질문: MemTable이 커질수록 Write Stall이 줄어드는데, 어느 크기에서 포화하는가?

  예상 메커니즘:
    MemTable 작음 → flush 잦음 → L0 파일 급속 누적
                 → level0_slowdown(20) 초과 → Stall 시작
                 → level0_stop(36) 초과   → Stall 심화

    MemTable 커짐 → flush 드물어짐 → L0 파일 천천히 쌓임
                 → Compaction이 따라잡음 → Stall 감소
                 → 일정 크기 이후 추가 증가해도 효과 미미 → "포화"

  시나리오 (8개 × N_RUNS=3 = 24런):
  ─────────────────────────────────────────────────────────────────────────────
  Exp ID        write_buffer_size    크기     비고
  ─────────────────────────────────────────────────────────────────────────────
  mem_2mb       2,097,152            2MB      기존 실험 최악 케이스
  mem_4mb       4,194,304            4MB
  mem_8mb       8,388,608            8MB
  mem_16mb      16,777,216           16MB
  mem_32mb      33,554,432           32MB
  mem_64mb      67,108,864           64MB     RocksDB 기본값
  mem_128mb     134,217,728          128MB
  mem_256mb     268,435,456          256MB
  ─────────────────────────────────────────────────────────────────────────────

  예상 결과 형태 (OPS vs MemTable 크기):

    OPS
      ↑                                         ● ─── ●
    30K│                                   ●───●
    25K│                             ●───●
    20K│                       ●───●
    15K│                 ●
    10K│           ●
     7K│     ●
         └──────────────────────────────────────────────→ MemTable
         2MB  4MB  8MB  16MB  32MB  64MB  128MB  256MB
                         ↑
                    이 "무릎(knee)"를 찾는 것이 목표

  시각화 (aggregate_memtable.py) — 4개 그래프:
    1. 평균 OPS vs MemTable 크기 (log x축) — 포화 지점 식별
    2. 누적 Write Stall 시간 vs MemTable 크기 — 0에 수렴하는 지점
    3. WAF vs MemTable 크기 — 크기 증가에 따른 증폭 변화
    4. OPS 시계열 멀티라인 — 각 크기별 쓰기 처리량 시간 변화

  예상 소요 시간:
    2MB: 3런 × 약 1800s = 90분
    4~32MB: 점진적 감소
    64~256MB: 3런 × 약 450s = 22분
    전체: 약 3~5시간


================================================================================
 [Part 2: Compaction 조건 변화 실험]  —  run_compaction_exp.sh
================================================================================

  연구 질문: Compaction 조건을 어떻게 조정하면 Write Stall과 Read/Write 증폭을
             동시에 최적화할 수 있는가?

  공통 기준 (모든 서브실험 공통 베이스라인):
    --write_buffer_size=67108864 (64MB, 기본값)
    --threads=4, --num=2500000 (per thread)

  ─────────────────────────────────────────────────────────────────────────────
  [2-A] 백그라운드 Compaction 스레드 수  (4시나리오 × 3런 = 12런)
  ─────────────────────────────────────────────────────────────────────────────
  가설: 스레드 수 증가 → Compaction 속도 향상 → L0 적체 감소 → Stall 감소
        단, 스레드 증가에 따른 CPU 경합으로 수확 체감 발생

  Exp ID      max_background_jobs    설명
  ──────────────────────────────────────────────────────────────────────────
  comp_bg1    2                      플러시1 + 컴팩션1 (최소)
  comp_bg2    3                      플러시1 + 컴팩션2
  comp_bg4    5                      플러시1 + 컴팩션4
  comp_bg8    9                      플러시1 + 컴팩션8 (적극적)

  ─────────────────────────────────────────────────────────────────────────────
  [2-B] L0 파일 수 트리거 임계값  (5시나리오 × 3런 = 15런)
  ─────────────────────────────────────────────────────────────────────────────
  가설: 임계값 높임 → Stall 발동 늦어짐 → 단기 처리량 향상
        단, L0 파일 누적 허용 → Read 시 더 많은 파일 검색 → RAF 증가

  Exp ID          slowdown    stop    설명
  ──────────────────────────────────────────────────────────────────────────
  comp_l0_4_8     4           8       매우 타이트 (조기 Stall)
  comp_l0_12_24   12          24      타이트
  comp_l0_20_36   20          36      기본값
  comp_l0_40_80   40          80      널널 (Stall 지연)
  comp_l0_80_160  80          160     매우 널널 (Stall 거의 없음)

  핵심 Trade-off:
    임계값 낮음  → 잦은 Stall, 낮은 WAF, 높은 Read 성능
    임계값 높음  → 드문 Stall, 높은 WAF, 낮은 Read 성능 (L0 파일 많음)

  ─────────────────────────────────────────────────────────────────────────────
  [2-C] 레벨 크기 및 배율 조정  (4시나리오 × 3런 = 12런)
  ─────────────────────────────────────────────────────────────────────────────
  가설: L1 크기가 작으면 → 자주 컴팩션 → WAF 증가, 하지만 Stall 패턴 변화
        L1 크기가 크면  → 드물게 컴팩션 → 낮은 WAF, 하지만 한 번에 큰 부하

  Exp ID             L1 base    multiplier    설명
  ──────────────────────────────────────────────────────────────────────────
  comp_lvl_small     64MB       5             레벨 작음, WAF 높음 예상
  comp_lvl_default   256MB      10            기본값
  comp_lvl_large     1024MB     10            레벨 큼, 컴팩션 드물음
  comp_lvl_mult20    256MB      20            레벨당 20배 증가, 레벨 수 감소

  ─────────────────────────────────────────────────────────────────────────────
  [2-D] Compaction 알고리즘  (2시나리오 × 3런 = 6런)
  ─────────────────────────────────────────────────────────────────────────────
  가설: Universal Compaction은 WAF가 낮지만 공간 증폭이 크고
        컴팩션이 더 폭발적으로 발생할 수 있음

  Exp ID                  compaction_style    설명
  ──────────────────────────────────────────────────────────────────────────
  comp_style_leveled      0                  Level-based (기본값)
  comp_style_universal    1                  Universal (WAF 감소 목적)

  ─────────────────────────────────────────────────────────────────────────────
  [2-E] Pending Compaction 바이트 임계값  (4시나리오 × 3런 = 12런)
  ─────────────────────────────────────────────────────────────────────────────
  가설: Pending Compaction 부채가 임계값 초과 시 Stall 발동.
        임계값 낮으면 → 조기 Stall, 역설적으로 Compaction 부채 억제
        임계값 높으면 → Stall 늦게 발동, 부채 누적 허용 → 더 큰 폭발 위험

  Exp ID                soft_pending    hard_pending    설명
  ──────────────────────────────────────────────────────────────────────────
  comp_pend_very_tight  64MB            256MB           소량 부채에도 Stall
  comp_pend_tight       512MB           2GB             타이트
  comp_pend_loose       4GB             16GB            널널
  comp_pend_default     64GB            256GB           기본값 (사실상 미발동)

  ─────────────────────────────────────────────────────────────────────────────
  총 Compaction 실험:
    2-A: 4시나리오 × 3런 = 12런
    2-B: 5시나리오 × 3런 = 15런
    2-C: 4시나리오 × 3런 = 12런
    2-D: 2시나리오 × 3런 =  6런
    2-E: 4시나리오 × 3런 = 12런
    합계: 19시나리오 × 3런 = 57런 (약 8~10시간)
