## 섹션 1: 주제와 가설 소개

**주제:** RocksDB 블록 캐시 히트율(Hit Rate)과 읽기 요청 분포의 관계 분석

**연구 동기:**
RocksDB는 오픈소스 고성능 key-value 저장 엔진으로, 내부에 블록 캐시를 통해 자주 접근되는 데이터를 메모리에 보관해 디스크 읽기를 줄인다.
실제 서비스에서 읽기 요청이 어떤 패턴으로 들어오느냐에 따라 캐시 효율이 크게 달라질 것이라는 문제의식에서 출발했다.

**핵심 가설:**
"읽기 요청이 특정 키 구간에 집중될수록(분포가 뾰족할수록) Block Cache Hit Rate가 높아질 것이다."

**가설의 근거:**
- 캐시는 한정된 메모리(32MB)를 가짐
- 접근이 소수의 키에 집중 → 그 키들이 캐시에 계속 머물며 반복 HIT
- 접근이 전체 키에 분산 → 캐시 용량 초과로 교체 빈번 → HIT 감소

## 섹션 2: 실험 파라미터와 과정 소개

**실험 환경:**
- 플랫폼: Linux, RocksDB 최신 버전
- 언어: C++ (reader/writer), Python (분석 및 시각화)
- 캐시 타입: HyperClockCache (RocksDB 기본값)

**실험 파라미터:**
| 파라미터 | 값 | 설명 |
|---|---|---|
| NUM_KEYS | 100,000개 | 전체 키 수 |
| VALUE_SIZE | 1KB | 키당 값 크기 |
| 총 DB 크기 | 약 100MB | NUM_KEYS × VALUE_SIZE |
| NUM_REQUESTS | 50,000회 | 실험당 읽기 요청 수 |
| 캐시 기준값 | 32MB | RocksDB 기본 캐시 크기 |
| 캐시 스윕 범위 | 4, 8, 16, 32, 64, 128, 256 MB | 7단계 |
| 총 실험 횟수 | 1,506회 | 통계적 신뢰 확보 |

**실험 과정:**
1. writer 실행: DB에 키 100,000개 삽입 → Flush + CompactRange로 MemTable을 SST 파일로 완전 내림 (MemTable 영향 제거)
2. reader 실행: 각 워크로드별 50,000건 읽기 → BLOCK_CACHE_HIT / BLOCK_CACHE_MISS 측정
3. 1,506회 반복 → 평균, 표준편차, 신뢰구간 계산
4. Python으로 시각화 및 통계 분석

**측정 지표:**
Hit Rate(%) = BLOCK_CACHE_HIT / (BLOCK_CACHE_HIT + BLOCK_CACHE_MISS) × 100

**통계적 신뢰도 확인:**
- n=6: 표준편차 ±38% (신뢰 불가)
- n=1,006: 표준편차 ±3% 이내로 수렴
- n=1,506: n=1,006과 평균 차이 0.1%p 미만 → 충분히 수렴됨

## 섹션 3: 캐시 내 히트의 구조적 원리

### SSTable 파일 구조

RocksDB의 데이터는 SSTable(Sorted String Table) 파일에 저장되며, 3가지 핵심 블록으로 구성된다.

| 블록 | 역할 |
|---|---|
| Data Block | 실제 Key-Value 데이터가 정렬된 상태로 저장. SSTable 파일의 대부분을 차지 |
| Index Block | 각 데이터 블록의 오프셋과 키 범위를 저장하는 메타데이터. 데이터 탐색 진입점 |
| Filter Block | SSTable 내 키 존재 가능성을 판별하는 블룸 필터(Bloom Filter). 불필요한 I/O 사전 차단 |

**데이터 접근 흐름 (ACCESS FLOW):**
```
STEP 1: 접근하고자 하는 SST에 히트
    ↓
STEP 2: Index Block이 실제 데이터 블록 위치를 가리킴
        (또는 데이터 블록 직접 히트 시 완료)
    ↓
STEP 3: 대상 Data Block 직접 접근 (I/O)
```

### Sharded Block Cache 구조

RocksDB의 Block Cache는 전체 용량을 여러 Shard로 나누어 관리한다.
- 각 Block은 Hash 함수를 통해 특정 Shard에 배정됨
- 각 Shard는 독립적인 LRU list와 Hash table을 가짐
- 분산 관리로 lock contention 감소 → 동시성 성능 향상

### Index Block의 캐시 점유 문제

캐시에 Data Block만 올릴지, Index Block도 함께 올릴지가 성능에 영향을 준다.

**Data Block 직접 히트:** 요청한 Key가 캐시 내 데이터 블록에 즉시 존재 → 최저 지연시간

**Index Block 히트:** 캐시된 Index Block으로 데이터 블록 위치를 먼저 확인 → 인덱스는 캐시, 실제 데이터는 디스크에서 로드

| 구분 | 전체 캐시 히트(Index 포함) | 순수 Data Block 히트 |
|---|---|---|
| 측정값 | 92% | 85% |
| 차이 | Δ약 7% |  |

### 본 실험에서의 결정

**의문:** Index Block의 캐시 점유가 실험 결과에 영향을 주지 않았을까?

**측정 결과:** Index Block 포함 vs 미포함 시 Hit Rate 차이 = **0.1~1% 수준**

**결정:** Tradeoff를 고려했을 때:
- Index Block 포함 → 안정적인 읽기 성능(Latency) 보장, 실험 재현성 확보
- Index Block 제외 → 캐시 용량 효율 소폭 향상, 단 캐시 미스 시 랜덤 I/O 급증 위험

→ **안정성 우선으로 Index Block 포함 방식으로 진행** (실험 결과에 미치는 영향 미미)

## 섹션 4: 각각의 읽기 분포에 대한 상세한 설명

총 10가지 정적 워크로드 + 4가지 동적 워크로드를 실험함.

### 정적 워크로드 (접근 패턴이 실험 내내 고정)

**1. Uniform (균등 분포)**
- 모든 키에 동일한 접근 확률
- 캐시 재사용이 가장 어려운 최악 조건
- 실제 예시: 무작위 레코드 샘플링, 통계 계산

**2. Sequential (순차 분포)**
- key_0부터 순서대로 접근 (key_0, key_1, key_2, ...)
- 같은 키를 반복 접근하지 않음
- 실제 예시: 테이블 풀스캔, 백업/복원, ETL

**3. Gaussian_s05 (가우시안, σ=5%)**
- 중앙(key_50000) 주변에 집중, 표준편차 5% (5,000개 키)
- 실질 Working Set ≈ 30MB
- 실제 예시: 특정 가격대 상품 집중 조회

**4. Gaussian_s10 (가우시안, σ=10%)**
- 중앙 주변 집중, 표준편차 10% (10,000개 키)
- 실질 Working Set ≈ 60MB
- σ가 2배 → Working Set도 2배

**5. Zipfian_a10 (지프 분포, α=1.0)**
- 순위 r인 키의 접근 확률 ∝ 1/r (강한 쏠림)
- "1위 키가 2위보다 2배, 3위보다 3배 많이 접근"
- 실제 예시: SNS 인기 게시물, 검색 키워드 빈도

**6. Zipfian_a05 (지프 분포, α=0.5)**
- 약한 쏠림, Uniform에 가까운 형태
- 집중도 낮아 캐시 효율 감소

**7. Hotspot_8020 (핫스팟 80:20)**
- 상위 20% 키(20,000개)에 요청의 80% 집중
- hot/cold 구역 경계가 명확한 계단 형태
- 실제 예시: 특정 카테고리 집중 쇼핑몰

**8. Hotspot_9505 (핫스팟 95:05)**
- 상위 5% 키(5,000개)에 요청의 95% 집중
- Working Set ≈ 5MB → 8MB 캐시만으로 포화
- 실제 예시: 바이럴 콘텐츠, 베스트셀러

**9. Bimodal (이중 피크 분포)**
- 25% 지점과 75% 지점에 각각 피크
- 두 피크의 Working Set 합산 ≈ 30~60MB
- 실제 예시: 오전/오후 두 번의 피크 트래픽

**10. Latest (최신 편향)**
- 키 번호가 클수록(최신 키) 더 자주 접근
- 접근 범위가 넓어 캐시 효율 낮음
- 실제 예시: 소셜 타임라인 피드, 최근 주문 내역

### 동적 워크로드 (실험 도중 패턴이 이동)

배치(Batch) 단위로 시간 경과에 따른 분포 변화를 측정.
전반부 25,000건은 피크 A 분포, 후반부 25,000건은 피크 B 분포.

| 워크로드 | 이동 거리 | 분포 폭(σ) | 특징 |
|---|---|---|---|
| moving_gaussian020805 | 20%→80% (60%p) | σ=5% | 원거리 이동, 좁은 분포 |
| moving_gaussian020810 | 20%→80% (60%p) | σ=10% | 원거리 이동, 넓은 분포 |
| moving_gaussian030705 | 30%→70% (40%p) | σ=5% | 근거리 이동, 좁은 분포 |
| moving_gaussian030710 | 30%→70% (40%p) | σ=10% | 근거리 이동, 넓은 분포 |

## 섹션 5: 예상 적중한 Case

**결과 요약 (32MB 캐시, n=1,506회):**
| 순위 | 워크로드 | Hit Rate | 가설 예상 | 판정 |
|---|---|---|---|---|
| 1위 | Hotspot_9505 | 92.69% | 90%+ | ✓ 적중 |
| 2위 | Gaussian_s05 | 87.22% | 85%+ | ✓ 적중 |
| 3위 | Zipfian_a10 | 80.49% | 80%+ | ✓ 적중 |
| 4위 | Hotspot_8020 | 70.69% | 70%+ | ✓ 적중 |
| 7위 | Gaussian_s10 | 69.14% | 65~75% | ✓ 적중 |
| 8위 | Zipfian_a05 | 41.44% | 40~50% | ✓ 적중 |
| 9위 | Latest | 29.69% | 30%- | ✓ 적중 |
| 10위 | Uniform | 28.02% | 최저 | ✓ 적중 |

**핵심 발견:**
- 동일한 32MB 캐시에서 최고(92.7%) vs 최저(28.0%) = 3.3배 차이
- Hotspot_9505: 8MB 캐시만으로 포화 → 전체 데이터의 5%만 캐시로 92% 달성
- Zipfian_a10: 4MB(전체의 4%) 캐시에서 이미 66.9% → 투자 대비 효과 최고

**캐시 크기별 포화점:**
- Hotspot_9505: 8MB에서 포화 (Working Set = 5MB)
- Gaussian_s05: 32MB에서 포화 (Working Set ≈ 30MB)
- Gaussian_s10: 64MB에서 포화 (Working Set ≈ 60MB)

**결론:** 가설 대로, 접근이 집중될수록 적은 캐시로도 높은 효율 달성 가능.

## 섹션 6: 예상 실패한 Case

### Case 1: Bimodal (쌍봉형) — 예상보다 낮음

**예상:** 두 구간에 집중되므로 Hit Rate 80% 이상
**실제:** 69.25% (예상보다 약 11%p 낮음, Gaussian_s10과 거의 동일)

**원인 분석 — Working Set이 두 배로 늘어난다:**
- Gaussian_s05(단일 피크): Working Set ≈ 30MB → 32MB 캐시에 수용 가능
- Bimodal(이중 피크): 피크 1(25% 지점) + 피크 2(75% 지점) = 합산 Working Set ≈ 30~60MB
- 두 피크를 오가며 접근할 때, LRU 캐시가 1번 피크 블록을 교체하고 2번 피크 블록을 올리는 과정을 반복 (캐시 thrashing)
- 캐시를 64MB로 늘리면 77.6%로 회복 → 32MB가 부족했던 것이 원인임을 확인

**핵심 교훈:**
"집중된 구간이 여러 개여도, 총 Working Set이 캐시 크기를 초과하면 효율이 떨어진다"
적정 캐시 크기 = 각 피크의 Working Set 합산

---

### Case 2: Sequential (순차 접근) — 예상보다 훨씬 높음

**예상:** 같은 키를 반복 접근하지 않으므로 Hit Rate 낮을 것 (30%대)
**실제:** 74.95% — 예상보다 약 45%p 높음. 그리고 캐시 크기(4MB~256MB)와 완전히 무관.

**원인 분석 — 블록 내 공간 지역성(Spatial Locality):**

가설의 착각: "Sequential은 같은 키를 반복하지 않는다" → 이것은 사실
그러나 RocksDB의 캐시 단위는 키(Key)가 아니라 블록(Block, 4KB)임.

블록당 약 4개의 키가 담김 (키 1KB + 블록 4KB):
```
key_0 접근 → 블록[0](key_0~key_3) 디스크 읽기 → MISS, 캐시에 적재
key_1 접근 → 블록[0]이 이미 캐시에 있음 → HIT
key_2 접근 → 블록[0]이 이미 캐시에 있음 → HIT
key_3 접근 → 블록[0]이 이미 캐시에 있음 → HIT
key_4 접근 → 블록[1](key_4~key_7) → MISS
```

이론적 Hit Rate = (블록당 키 수 - 1) / 블록당 키 수 = 3/4 = 75.0%
실측값 74.95% → 이론값과 완벽히 일치!

**캐시 크기와 무관한 이유:**
순차 접근은 각 블록을 딱 한 번씩만 읽음. 캐시가 크든 작든 재사용이 발생하지 않으므로 캐시 용량이 영향을 미치지 못함.

**핵심 교훈:**
"키 반복 없음"이 아니라, 블록 크기 / 키 크기 비율이 Sequential의 Hit Rate를 결정한다.

---

### 가설 보완: 3가지 법칙 도출

| 법칙 | 내용 |
|---|---|
| 집중도 법칙 | 접근이 집중될수록 hit율 높음. 단, Working Set ≤ 캐시 크기일 때만 성립 |
| 공간 지역성 법칙 | 키 반복 없어도 블록 내 인접 키가 함께 로드되어 hit 발생 (Sequential의 비밀) |
| Working Set 법칙 | Working Set > 캐시 크기이면 집중도와 무관하게 hit율 저하 (Bimodal의 원인) |

## 섹션 7: 느낀점 — 동적 분포 실험에서 발견한 것들

### 배경: 동적 워크로드란?

정적 분포는 실험 내내 패턴이 고정되지만, 실제 서비스는 시간대에 따라 접근 패턴이 바뀐다.
Moving Gaussian 실험은 이 현실을 반영해, 배치 중간에 분포의 피크가 이동할 때 LRU 캐시가 어떻게 반응하는지를 측정했다.

### 발견 1: 이동 거리 vs 분포 폭 — 각각 다른 측면에 영향을 준다

**분포의 이동 거리** → 분포 이동 시 hit rate의 **일시적 하락폭**을 결정한다.
- 이동 거리가 클수록(20→80%, 60%p) 배치 5에서 더 급격히 떨어짐
- 이동 거리가 작을수록(30→70%, 40%p) 하락폭이 완만함

**분포의 폭(σ)** → 분포 이동 후 **안정화된 hit rate의 상한**을 결정한다.
- σ=5%: 안정화 후 93~97% 수렴
- σ=10%: 안정화 후 75~79% 수렴
- σ=15%: 안정화 후 59~60% 수렴

```
이동 거리는 일시적인 성능 하락폭에 영향을 주고,
분포 폭은 이후 안정화된 뒤의 hit rate에 더 큰 영향을 준다.
```

### 발견 2: LRU 캐시는 반드시 회복된다

- 분포가 이동해도 LRU 캐시는 새 분포에 적응하며 hit rate를 회복함
- warm-up(초기 적재)보다 재적응 과정이 느린 이유:
  - warm-up: 빈 캐시 → 새 블록 채우기 (방해 요소 없음)
  - 재적응: 기존 캐시에 남은 구 분포 블록들이 eviction될 때까지 새 블록과 경쟁

### 발견 3: 재적응이 반복될수록 느려지지 않는다

가설: "warm-up보다 재적응이 느리다면, 재적응이 반복될수록 더 느려질까?"

**실험 (2단계 분포 이동):** 피크 A → 피크 B → 피크 A로 2회 이동 측정

**결과:** 재적응이 반복되어도 느려지지 않음
- 오히려 이전 캐시에 남아 있는 블록과 새 분포의 overlap 덕분에 더 나은 출발점에서 시작 가능

### 발견 4: 이동 방향은 결과에 무관하다

역순(피크 B → A)으로 이동해도 정순(A → B)과 거의 동일한 패턴을 보임.
LRU 캐시의 방향 무관성 확인 — 접근 분포가 어느 방향으로 이동하든 동일하게 적응.

### 동적 실험의 핵심 결론

| 요소 | 영향을 받는 지표 |
|---|---|
| 이동 거리 | 분포 이동 직후 일시적 hit rate 하락폭 |
| 분포 폭(σ) | 안정화 후 최종 hit rate 상한 |
| 이동 방향 | 영향 없음 (LRU 방향 무관) |
| 재적응 반복 | 느려지지 않음, 오히려 overlap 효과로 개선 가능 |

## 섹션 8: 다음 주제 — Write Stall과 Compaction 속도 측정

**배경:**
이번 실험은 읽기(Read) 관점에서 캐시 효율을 측정했다.
그러나 RocksDB의 성능에는 쓰기(Write) 측면도 매우 중요하다.

**Write Stall이란?**
RocksDB에 쓰기 요청이 너무 빠르게 들어오면, MemTable이 가득 차거나 Level 0 파일이 너무 많아져 Compaction이 따라가지 못하게 된다. 이때 RocksDB가 쓰기를 의도적으로 늦추거나 멈추는 현상이 Write Stall이다.

**Compaction이란?**
여러 레벨의 SST 파일을 병합·정렬하여 읽기 효율을 높이는 백그라운드 작업이다.
Compaction이 느리면 Level 0 파일이 쌓여 Write Stall을 유발하고, 읽기 성능도 저하된다.

**계획하는 실험:**
1. 다양한 쓰기 속도(write rate)에서 Write Stall 발생 시점 측정
2. Compaction 속도와 쓰기 처리량(write throughput)의 관계 분석
3. 다양한 Compaction 설정(Level 수, 파일 크기, 병렬 스레드 수) 변화에 따른 성능 비교
4. Write Stall 발생 시 읽기 성능에 미치는 영향 측정

**기대 결과:**
쓰기 집중 워크로드에서 Compaction 튜닝이 전체 처리량에 미치는 영향을 정량화하고,
최적 Compaction 설정 가이드라인 도출
